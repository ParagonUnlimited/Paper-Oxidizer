## 🤖 Claude

Looking at this diff, the only substantive change is moving `SESSION_SECRET` from a UI-managed credential to a Coolify-generated value bound via `${SERVICE_HEX_SESSION}` (32 hex chars = 128 bits of entropy).

Let me trace what could go wrong:

1. **Entropy**: 32 hex chars = 128 bits. Adequate for cookie signing (HMAC). Not a finding.
2. **Empty-string fallback if unset**: `${SERVICE_HEX_SESSION}` expands to empty if unset (e.g., local `docker compose` without Coolify), which would set `SESSION_SECRET=""`. But this is a local-dev concern; whether the app fail-closes on empty is app-level code, not a compose defect. The diff doesn't introduce that risk — previously SESSION_SECRET was unset (also empty) if Coolify wasn't providing it.
3. **Coolify SERVICE_HEX_ naming**: The suffix `SESSION` is per-compose-project scoped in Coolify, not a global shared secret. Not attacker-controllable.
4. **Rotation friction**: Binding SESSION_SECRET to the compose file makes it read-only in the Coolify UI — the file itself flags this same pattern as the reason NEON_DATABASE_URL etc. are NOT in compose. But SESSION_SECRET is generated, not a rotatable credential, and the comment explicitly justifies the tradeoff. Operational, not a vulnerability.
5. **No new sinks, sources, or gates**: No shell/exec/SQL/path/URL/HTML/log surfaces are touched. No permission changes. No entry point exposure change (still `expose`, not `ports`).
6. **env_file with `required: false`**: Unchanged from before; documented for local dev.
